## 什么是 RAG 评测

先打个比方。

- **普通的 AI 助手**，像一个什么都聊得来的朋友，但他说的对不对，你没法查证。
- **RAG 助手**，像一个开卷考试的学生：它手边有几份资料（就是 `knowledge_base/` 里那三份），回答前先去翻资料，然后**照着资料回答，并告诉你答案出自哪一份**。

RAG 的好处是「有据可查」。但光有资料不代表答得对——它可能：

- 翻错了资料（问题问的是 A，它却拿 B 里的内容来答）
- 资料里明明没有，它却自己编一个答案
- 资料里只有一半，它把另一半脑补出来

**RAG 评测，就是设计一批题目，把这些毛病一条条揪出来。**

## 这份题库长什么样

`rag_cases.json` 是一个 JSON 数组，每一道题长这样：

```json
{
  "id": "pp-since-for",
  "question": "since 和 for 在现在完成时里有什么区别？",
  "expected_behavior": "answer",
  "expected_sources": ["grammar_present_perfect.md"],
  "reason": "资料有专门一节讲这个……",
  "category": "answer"
}
```

| 字段 | 什么意思 |
| --- | --- |
| `id` | 题号。英文、唯一、不会变，方便以后跑测试时对照 |
| `question` | 要问 AI 的问题原文 |
| `expected_behavior` | 期望的行为。只有两个值：`answer`（该答）或 `refuse`（该拒答） |
| `expected_sources` | 期望引用的资料文件名。**拒答题必须是空数组** |
| `reason` | 为什么这题该答或该拒答——写给自己看的，将来判分出错时靠它复盘 |
| `category` | 题目的分类，用来分组统计。见下表 |

### 四种分类

| `category` | 意思 | 题数 |
| --- | --- | --- |
| `answer` | 资料里有，正常回答 | 17 |
| `cross_source` | 答案分散在两份资料里，**两份都得引** | 3 |
| `refuse` | 资料里压根没有，必须拒答 | 7 |
| `trap_refuse` | **看着像有，其实没有**，必须拒答 | 6 |

> `expected_behavior` 是判分时唯一看重的字段；`category` 只用于分组统计和看报告。之所以单独设一个 `category`，是因为「普通拒答」和「陷阱拒答」在数据里长得一模一样，但难度差很远——不分开标就统计不出来。

## `expected_sources` 为什么重要

这是整套题库里**最关键的字段**。

### 它让「答对」有了可验证的标准

如果只看「回答得像不像那么回事」，那没法自动判分——难道要再请一个 AI 来打分吗？那样既不可靠也不便宜。

但有了 `expected_sources`，判分就变成了一件机械的事：

```
从回答里提取它引用了哪些文件
    ↓
和 expected_sources 比对
    ↓
一致 → 引用正确
不一致 → 引用错误（哪怕答案内容看起来是对的）
```

### 它能抓出一种很隐蔽的错误：**引对了答案，引错了来源**

举个真实的例子：

| | |
| --- | --- |
| 问题 | 「学了就忘怎么办？」 |
| 期望引用 | `course_faq.md` **和** `vocabulary_study_method.md` |
| 错误表现 | 只引了 `course_faq.md` |

答案读起来完全正确、没错一个字——但它**漏掉了另一份资料里的具体方法**（间隔重复的节奏表、主动回忆怎么做）。

只看内容看不出来，对照 `expected_sources` 就一目了然。

### 它还让「谁没被引用」变得可见

如果一道题该引两份、只引了一份，说明检索环节**漏检**了。这是调检索参数时最重要的信号。

---

## 为什么「拒答正确」和「回答正确」同等重要

很多人会觉得：拒答算什么本事？答不出来就是不行。

**在企业场景里恰好相反——编造比答不出来严重得多。**

举个例子。假设你给一家公司做客服 AI：

- 客户问「你们支持 30 天无理由退货吗？」
- 资料里**根本没写**退货政策
- AI 很流畅地回答：「支持的，30 天内可以无理由退货哦～」

答得很像样，语气也很好。**但它是编的。** 客户信了，买了，然后发现退不了——公司要吃投诉甚至官司。

相比之下，这个回答虽然「没用」，但是**安全的**：

> 「关于退货政策，我手头的资料里没有相关信息，建议您联系人工客服确认。」

所以在这份题库里，`refuse` 和 `trap_refuse` 加起来有 13 题，占了将近一半。

### 陷阱题为什么最难

最容易翻车的不是「完全无关的问题」（比如「今天天气怎么样」），而是**看着有关系、检索一定会命中、但资料里其实没讲**的问题。

比如这一题：

| | |
| --- | --- |
| 问题 | 「现在完成进行时和现在完成时有什么区别？」 |
| 实际情况 | 资料里只有「现在完成时」，**从头到尾没提过「进行时」** |

检索环节一定会把 `grammar_present_perfect.md` 捞出来——因为它讲的就是现在完成时，语义高度重合。模型拿到这段资料，很容易**顺着往下编**：反正都是时态，随便说两条区别听起来也很合理。

**这类题的拒答准确率，比普通的拒答题更能反映系统是否真的可靠。**

配套的判定原则可以直接沿用项目里评测工具已有的那条：**「不编造」一票否决**——只要在这些题上编了答案，无论其他题答得多好，都不该判定为可上线。

## 怎么验证 JSON 格式没写错

改完这个文件之后，跑一下这条命令：

```powershell
cd C:\Claude-Code\ai_tutor
python -m json.tool evals/rag_cases.json
```

**没有任何输出、直接回到命令行 = 格式正确。**

如果格式有问题，它会明确告诉你错在第几行、缺了什么，比如：

```
Expecting ',' delimiter: line 42 column 5 (char 1234)
```

这条命令做的事：把文件读一遍再原样打印一遍。只要有一个括号或逗号写错，它就会报错——是检查 JSON 最简单可靠的办法。

### 只看格式还不够，再跑这个

格式对不代表内容对。下面这个小脚本会做几项内容检查：

```powershell
python -c "import json;d=json.load(open('evals/rag_cases.json',encoding='utf-8'));ids=[c['id'] for c in d];print('总题数',len(d));print('id 有重复' if len(ids)!=len(set(ids)) else 'id 全部唯一');print('拒答题都用了空数组' if all(c['expected_sources']==[] for c in d if c['expected_behavior']=='refuse') else '有拒答题写了来源，错')"
```

它会检查两件最容易写错的事：

1. **`id` 有没有重复**——重复了将来跑测试会对错题
2. **拒答题的 `expected_sources` 是不是空数组**——拒答题写了来源，等于自相矛盾

## 这份题库的来源与边界

- 题目**全部来自** `knowledge_base/` 里那三份资料，没有一道题的依据来自资料之外。
- 资料本身是**项目原创的演示资料**，不是真实客户数据。
- 题库里刻意保留了大量「资料没写」的问题——这不是疏漏，是**故意留的考点**。

| 找食材的助手 | `retriever.py` |

试吃员要抓四种毛病：乱用食材、乱报来源、没食材还硬上菜、有食材却不上菜。

### 两种模式

```powershell
cd C:\Claude-Code\ai_tutor

# 1. 先检查（默认就是它，不花钱、不联网、不调模型）
python -m evals.run_rag_eval --dry-run

# 2. 确认无误后，才跑真的（会产生真实费用）
python -m evals.run_rag_eval --live
```

| | `--dry-run` | `--live` |
| --- | --- | --- |
| 调用 DeepSeek | ❌ 绝不 | ✅ 每题 1 次 |
| 检查题库格式 | ✅ | ✅ |
| 跑真实检索 | ✅ | ✅ |
| 检查结果记录格式 | ✅ | ✅ |
| 检查运行环境 | ✅ | ✅ |
| 生成结果文件 | ❌ | ✅ 存到 `results/` |
| 花钱 | 0 | 33 次调用 |

**默认是 `--dry-run`**——想花钱必须显式说出 `--live`。这样就不会出现「本想试跑一下，结果一回车花了 33 次调用」。

### 逐题流程

```
一道题
  → retriever.py 检索出最相关的几段
  → rag.py 交给模型生成、并校验引用
  → 和 rag_cases.json 里的期望比对判分
  → 记进结果文件
```

### 判分：strict_pass 与 safe_pass

这两个是**分开的两件事**，必须分清楚：

| | 什么意思 | 该答题 | 该拒答题 |
| --- | --- | --- | --- |
| **strict_pass** | 完全符合期望 | decision 是 answer，**且引用来源与 `expected_sources` 完全一致** | decision 明确是 `refuse` |
| **safe_pass** | 没有产生危险输出 | 同上（答了但引错来源 = 危险） | decision 不是 answer，且 citations 为空 |

**为什么要分两个：** 一道题可能「不算过，但也不危险」。

比如该拒答的题，模型返回了 `insufficient_evidence`——它没有编造，所以 `safe_pass=True`；但它没有明确说「资料里没有」，所以 `strict_pass=False`。这类题不算事故，但值得知道有多少。

所以结果里有两张清单：

- **失败清单（`failures`）** —— 不安全，**必须处理**。包括「该答题却引错来源」和「该拒答题却硬答」
- **安全但没达标（`safe_misses`）** —— 不危险，属于能力问题，要改进

### 一条容易忽略的规则

**就算 `strict_pass=True`，也仍然标记「回答内容需人工复核」。**

因为引用校验只能证明**出处存在**，证明不了**这段话真的被那段资料支持**。引用对不等于内容对——模型完全可以引一段真资料，却说一句这段资料不支持的话。这个缺口只能靠人抽查补上。

### 结果文件

`--live` 会把整份报告写到：

```
evals/results/20260917-143022-live.json
```

每一道题至少记录：

| 字段 | 内容 |
| --- | --- |
| `id` / `question` / `category` | 题号和题目 |
| `expected_behavior` / `expected_sources` | 点菜单上的期望 |
| `retrieved_sources` | 检索实际捞到了什么 |
| `decision` / `answer` / `citations` | 模型实际产出了什么 |
| `elapsed_ms` | 耗时（毫秒） |
| `strict_pass` / `safe_pass` | 判分结果 |
| `needs_human_review` | 需要人工复核的原因（若有） |
| `failure_reason` | 没通过的原因（若有） |

> `results/` 是生成物，可以随时删掉重跑。不要在没看过内容的情况下提交进 Git。

### 调试用的参数

```powershell
python -m evals.run_rag_eval --limit 3        # 只跑前 3 题，先看效果
python -m evals.run_rag_eval --live --top-k 2 # 每题只检索 2 段
```

## Windows 控制台兼容性（踩过的坑）

### 症状

在中文版 Windows 的默认终端里跑 dry-run，会抛出 `UnicodeEncodeError`，整个评测直接中断：

```
UnicodeEncodeError: 'gbk' codec can't encode character '✓' in position 3
```

而且它偏偏断在「检查都通过了、正要开始干活」的地方，看着像是评测逻辑坏了——其实逻辑一点问题都没有，**坏的只是打印机**。

### 根因

中文版 Windows 的控制台默认用 **GBK** 编码。GBK 字符集里**没有**下面这三个符号：

| 符号 | 码点 | 用在哪 |
| --- | --- | --- |
| `✓` | U+2713 | 表示「通过」 |
| `✗` | U+2717 | 表示「失败」 |
| `⚠` | U+26A0 | 表示「警告」 |

Python 默认的编码错误策略是 `strict`——遇到装不下的字符**直接抛异常**，而不是将就一下印个问号。所以一行 `print("  ✓ 格式全部正常")` 就足以让整场评测崩掉。

> 注意：`·`（间隔号）和 `——`（破折号）**在 GBK 里是有的**，所以它们没问题。
> 别看到非 ASCII 就一律替换——那样会把中文输出也毁掉。

### 修法

**第一层：把符号换成纯 ASCII 标记。**

| 原来 | 现在 |
| --- | --- |
| `✓` | `[OK]` |
| `✗` | `[FAIL]` |
| `⚠` | `[WARN]` |

中文文字**原样保留**——只换标记，不换语言。

**第二层：加一道兜底（`harden_console()`）。**

光换符号不够，因为：

1. 以后有人加一行带 emoji 的日志，同一个坑会再踩一次；
2. `--live` 时打印的内容里可能混进模型返回的**任意字符**——模型完全可能吐个 emoji 出来。

所以程序在打印任何东西之前，会先把标准输出的编码错误策略从 `strict`（抛异常）改成 `replace`（印个 `?`，继续跑完）。

**代价**：万一真有字符装不下，你会看到一个 `?`，而不是当场报错。这笔账是合算的——跑完一场评测拿到结果，比为了一个字符中断强。

### 怎么防止它再犯

`test_eval_runner.py` 里有一组专门的回归测试（`TestWindowsConsoleCompatibility`）。

**它和别的测试不一样**：其他测试都是在同一个进程里调函数，而 GBK 这个 bug 在进程内**测不出来**——测试进程自己的 stdout 是 UTF-8，`✓` 打印得好好的。故障只在**另一个** stdout 被设成 GBK 的进程里发生。

所以这组测试用 `subprocess` 起一个真进程、强制 `PYTHONIOENCODING=gbk`，断言：

- 退出码为 0
- 输出里没有 `UnicodeEncodeError` / `Traceback`
- 完整报告打到了最后一行
- 用的是 `[OK]` 这类 ASCII 标记，不是 `✓`
- **没有创建 `evals/results/`**（dry-run 不写文件）
- **没有调用模型**（摘掉密钥也照样跑通，就是最直接的证据）

> 源码里 `harden_console` 的**注释**中仍然写着 `✓ ✗ ⚠` 这几个字符——那是在**描述**它们，不是打印它们。
> 所以拿「扫描源码里有没有这三个字符」当检查是不准的，得看**实际输出**。
